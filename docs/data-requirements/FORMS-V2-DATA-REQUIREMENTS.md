## 0. Purpose & Method

This document translates PRD-003's approved product decisions into conceptual data requirements — what information Forms V2 needs to hold, why, and how it relates to V1's existing data — without prescribing tables, keys, indexes, types, or endpoints. It does not reopen PRD-001, PRD-002, or PRD-003.

**Method used throughout:** for every proposed data element, a "Which approved requirement requires this?" check was performed. Where an answer exists, it's cited inline (Source PRD column). Where none exists, the element is marked **OPEN** rather than added — nothing below was invented because it seemed technically useful.

**Governing principle, restated from your instruction:** V2 extends the existing Form model; it does not create a second Form product. Every new concept below is tested against this — each is modeled as an attachment to or configuration of an existing V1 entity, never a parallel structure.

## C. Field / Data Requirements

### C.1 Form Capability Configuration

**The distinction your instruction called out is the load-bearing rule for this entire section:** _"Tenant is entitled to OTP"_ (a Billing fact, resolved live via the Entitlement Service) is not the same state as _"OTP is enabled on this Form"_ (a Forms-owned configuration fact — the tenant's stored intent). Forms V2 needs to hold the second; it must never store or cache the first.

| Entity                        | Field / Concept                                                                       | Purpose                                                                    | Required? | Source PRD                                                                                                | Status                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | --------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Form Capability Configuration | `otp_enabled` (or equivalent boolean concept)                                         | Whether OTP verification is turned on for this specific Form               | Required  | PRD-003 §10.1 Admin configuration behavior: _"Tenant Admin enables/disables ... per Form, when entitled"_ | CONFIRMED                                                                |
| Form Capability Configuration | `multi_step_enabled`                                                                  | Whether multi-step presentation is turned on for this Form                 | Required  | PRD-003 §10.2                                                                                             | CONFIRMED                                                                |
| Form Capability Configuration | `ai_qualification_enabled`                                                            | Whether AI Lead Qualification is turned on for this Form                   | Required  | PRD-003 §10.3                                                                                             | CONFIRMED                                                                |
| Form Capability Configuration | OTP requiredness sub-setting (mandatory-when-on vs. its own optional/required toggle) | Whether, once OTP is enabled, it's always mandatory or itself configurable | —         | PRD-003 §15 #1                                                                                            | **OPEN — carried forward exactly as PRD-003 left it, not resolved here** |

**How "enabled" and "entitled" combine at runtime (behavioral, restated not redefined):** a capability actually functions only when both are true — Form Capability Configuration's flag is `true` **and** a live Entitlement Resolution call returns Active. Neither fact is derived from or cached inside the other. This is what makes PRD-002 §12.1's "live, not cached" rule and PRD-003's enforcement principle (checked at Admin config, widget render, _and_ public submission-time) actually implementable — if Forms ever stored a snapshot of the entitlement result, a downgrade wouldn't take effect until that snapshot was refreshed, contradicting both approved documents.

**New question surfaced by this analysis, not addressed by either PRD:** does the `enabled` flag itself change when the entitlement becomes unavailable (downgrade), or does it stay `true` while simply being functionally inert (because the live entitlement check now returns non-Active)? Analyzed in §C.7, since it also determines what the downgrade-notice mechanism needs.

### C.7 Downgrade / Fallback Data (CONFIRMED This Pass)

**CONFIRMED: no new persistent data is required to make downgrade/fallback work.** The fallback behavior confirmed in `PRD-002` §11.1 and `PRD-003` §10.1–§10.3 is computed live, at the point of use, from (Form Capability Configuration's `enabled` flag) **AND** (a live Entitlement Resolution call). The governing rule (_"a downgrade removes the paid capability, not the entire published Form"_) is satisfied by the live check alone, the moment the entitlement stops returning Active.

**CONFIRMED: the `enabled` flag does not reset on downgrade — it stays `true`, functionally inert until re-entitled.**

```
enabled = true  +  entitlement = Active       → capability operates
enabled = true  +  entitlement = unavailable  → capability is inert / safe fallback applies
```

This preserves the tenant's configuration intent and avoids forcing them to reconfigure the Form after re-subscribing. No data write occurs on downgrade at all — the same stored flag simply produces a different outcome depending on the live entitlement check.

**CONFIRMED: entitlement restoration is automatic, no tenant action required.** The moment the live check starts returning Active again, the capability resumes functioning under the same `enabled = true` flag — this follows directly from the confirmed behavior above, not as a separate mechanism.

**CONFIRMED: no Forms-side downgrade audit/event log is required.** `PRD-002` §12.2's downgrade-notice requirement (_"what was disabled, when, and on which Form(s)"_) is satisfiable without new Forms-side history data: "which Forms are affected" is every Form currently showing `enabled = true` for the affected capability (queryable live, since the flag is never reset), and "when" is sourced from Billing's own Subscription State, which `PRD-002` §14.4 already confirms holds an effective-since timestamp. No audit infrastructure is introduced into Forms V2.

## D. Relationships

```
Form (V1, unchanged)
 ├─ Fields (V1, unchanged) — ordered, typed, required/optional — remain children of Form
 ├─ Steps (V2, new, CONFIRMED persistent) — attached to Form, not a replacement for Fields
 │    ├─ step order
 │    └─ references existing Form Fields (+ field order within the Step)
 └─ Form Capability Configuration (V2, new)
      ├─ otp_enabled ────────────► entitlement key: forms.otp_verification
      ├─ multi_step_enabled ─────► entitlement key: forms.multi_step
      └─ ai_qualification_enabled ► entitlement key: forms.ai_lead_qualification

Submission (V1, unchanged, immutable)
 └─► Lead (V1, unchanged, unconditional 1:1)
       └─► AI Qualification Result (V2, new) — 0 or 1 per Lead, enrichment only,
           existence-only signal (no separate state model)

External relationship (not a stored FK — a live call):
Form Capability Configuration flag (V2) + entitlement key
       ──► Billing Entitlement Resolution (PRD-002 §14.7/§15.1)
       ──► one of five states (PRD-002 §10.1): Active / Not available /
           Subscription inactive / Downgrade-disabled-with-fallback / Check failed
```

**Firm note on the Step/Field relationship:** Steps _reference_ Fields — they do not own them, and they are not Fields' parent. A Field's relationship to Form is unchanged whether or not the Form uses Steps at all.

No relationship above introduces a second Form, a second Lead type, or a second Submission concept — every V2 addition is either attached to Form (Capability Configuration, Steps) or an enrichment of Lead (AI Qualification Result), consistent with §F below.
